*Техническая глава отчёта / диссертации*

---

## 1. Цель датасета и постановка задачи

### 1.1 Зачем нужен синтетический датасет

Задача автоматического анализа первопричин (Root Cause Analysis, RCA) в суперкомпьютерном кластере требует размеченных данных: для каждого инцидента необходимо знать точный узел, ставший источником сбоя. На реальных производственных системах такая разметка практически недоступна — операторы редко документируют причину каждого инцидента с точностью до узла и временного шага. Поэтому построена синтетическая симуляция, воспроизводящая телеметрию кластера и позволяющая генерировать произвольное число обучающих примеров с точно известными метками.

Синтетический датасет выполняет три функции:
1. **Обучение** — предоставляет достаточный объём разнообразных примеров.
2. **Валидация** — позволяет измерять метрики RCA честно, без утечки разметки из обучающей выборки.
3. **Ablation study** — делает воспроизводимой любую модификацию пайплайна (изменение амплитуды, добавление новых паттернов), что невозможно на реальном кластере.

### 1.2 Формализация задачи

Каждый пример в датасете представляет **одну телеметрическую сессию** кластера: 90-шаговую симуляцию, итогом которой становится одна гетерогенная граф-структура данных (`HeteroData` из PyTorch Geometric). Примерно 60 % примеров — **фолтед** (с внедрённой неисправностью), остальные — **healthy** (штатный режим).

Задача модели — для каждого фолтед-графа определить ровно один **узел-первопричину (RC-узел)** среди всех кандидатов. Кандидатами являются узлы типов `cpu`, `gpu`, `ram`, `hdd`, `switch` (всего до ~500 узлов на граф). Healthy-графы исключаются из расчёта метрик Hit@k: они используются только для обучения модели распознавать нормальные паттерны.

**Формально**: дан граф $G = (\mathcal{V}, \mathcal{E})$ с гетерогенными узлами и рёбрами, каждый узел имеет вектор признаков $\mathbf{x}_v \in \mathbb{R}^{d_v}$. Модель должна присвоить узлам скор $s_v$ такой, что $\text{rank}(v_{\text{RC}}) = 1$ (RC-узел занимает первое место в ранжировании) как можно чаще.

## 2. Топология графа

### 2.1 Состав узлов

| Тип | Количество | Физический объект |
|-----|-----------|-------------------|
| `cpu` | 100 | Процессор на каждом из 100 хостов |
| `gpu` | 100 | GPU-ускоритель (один на хост) |
| `ram` | 100 | Оперативная память хоста |
| `hdd` | 100 | Дисковая подсистема хоста |
| `switch` | 6 | 4 leaf + 2 spine коммутатора |
| `job` | 500 | Задания в планировщике (SLURM) |
| `rca_context` | 1 | Виртуальный агрегирующий узел |
| **Итого** | **907** | |

Архитектура сети — топология **Spine-Leaf**: 100 хостов подключены к 4 leaf-коммутаторам (25 хостов на каждый), leaf-коммутаторы связаны со 2 spine-коммутаторами. Каждый хост выполняет в среднем по 5 заданий из 500 ($500 / 100 = 5$). Привязка host→leaf и job→host разыгрывается случайно для каждого графа (семя берётся из номера образца), что исключает позиционную утечку — модель не может запомнить, «какой индекс хоста обычно даёт сбои».

### 2.2 Типы рёбер

Граф содержит 16 типов рёбер, разделённых на три категории:

**Физические рёбра** (инфраструктурные связи, 10 типов):

| Исходный тип | Отношение | Целевой тип | Смысл |
|---|---|---|---|
| `cpu` | `connected_to` | `switch` | хост подключён к leaf-коммутатору |
| `gpu` | `connected_to` | `switch` | GPU через PCIe и сетевой адаптер |
| `ram` | `attached_to` | `cpu` | память присоединена к процессору |
| `hdd` | `attached_to` | `cpu` | диск подключён к хосту |
| `switch` | `uplink_to` | `switch` | leaf → spine |
| *(и 5 обратных зеркальных рёбер)* | | | |

**Логические рёбра** (планировщик, 2 типа):

| Исходный тип | Отношение | Целевой тип | Смысл |
|---|---|---|---|
| `job` | `executes_on` | `cpu` | задание выполняется на хосте |
| `cpu` | `rev_executes_on` | `job` | обратное ребро |

**Контекстные рёбра** (агрегация, 4 типа):

| Исходный тип | Отношение | Целевой тип | Смысл |
|---|---|---|---|
| `job` | `reports_to` | `rca_context` | все задания «докладывают» |
| `switch` | `reports_to` | `rca_context` | все коммутаторы «докладывают» |
| *(и 2 обратных)* | | | |

### 2.3 Зачем гетерогенный граф

Однородный граф с усреднёнными признаками потерял бы различие между типами узлов (CPU и HDD имеют разный физический смысл, даже если нормированы в один диапазон). Гетерогенный GNN выучивает **отдельный проекционный слой для каждого типа** узла и рёбра, что позволяет:

- использовать разные признаковые пространства (`cpu`: 8 признаков × 4 канала = 32D; `gpu`: 12 × 4 = 48D);
- разграничить пути распространения аномалии (физические vs логические);
- применять разные веса внимания для разных типов рёбер.

Рёбра физической топологии позволяют модели обнаруживать причинно-следственные зависимости: аномалия на `hdd` распространяется к `cpu` через `hdd→attached_to→cpu`, затем к заданиям через `cpu→rev_executes_on→job`. Физически правильная топология заставляет модель учить граф-контекст, а не статистические корреляции признаков.

### 3.2 Непрерывные и категориальные признаки

Признаки разделяются по суффиксу имени (константы `CONTINUOUS_SUFFIXES` и `CATEGORICAL_SUFFIXES` в `config.py`). Категориальные (`_flag`, `_encoded`, `_status`) обрабатываются отдельно: в здоровой симуляции они флипают с вероятностью 0.02 за шаг, в инъекции неисправности — участвуют только как фоновый шум (текущая реализация не инъектирует категориальные в основной цикл неисправности).

### 3.3 Четыре временны́х канала на признак

После симуляции 90 шагов для каждого непрерывного признака $f$ у узла $v$ хранится вектор из 4 компонент:

$$\mathbf{x}_{v,f} = [\underbrace{x_t}_{\text{value}},\ \underbrace{x_t - x_{t-1}}_{\text{delta\_short}},\ \underbrace{x_t - \text{EMA}_t}_{\text{delta\_long}},\ \underbrace{\text{Var}_{5}(x)}_{\text{rolling\_var}}]$$

где $\text{EMA}_t$ — экспоненциально взвешенное скользящее среднее с $\alpha = 0.0645$ (соответствует окну ~30 шагов):

$$\text{EMA}_t = (1 - \alpha)\,\text{EMA}_{t-1} + \alpha\,x_t$$

**`delta_long`** оказался наиболее информативным каналом: он измеряет отклонение текущего значения от «своего» долгосрочного среднего. Если признак растёт несколько шагов подряд (начало неисправности), `delta_long` принимает большое положительное значение, пока EMA не адаптируется. Именно этот канал служит основным сигналом аномалии в ранжировании узлов.

**`rolling_var`** вычисляется по последним 5 шагам и фиксирует локальную нестабильность — полезен для burst-паттернов (swap thrashing, пачечные CRC-ошибки).

Итоговая размерность вектора признаков узла: $d_v = F_v \times 4$, например для `cpu`: $8 \times 4 = 32$, для `gpu`: $12 \times 4 = 48$.

## 4. Временна́я симуляция

Реализована в `training_pipeline/dataset_generator.py`, функции `simulate_healthy_trajectory()` и `simulate_trajectory_with_fault()`.

### 4.1 Здоровая траектория

Каждый граф начинается с 90-шаговой симуляции здорового кластера:

1. **Инициализация**: для каждого узла $v$ и типа $\tau$ сэмплируется начальное значение из $\mathcal{N}(\mu_\tau, \sigma_\tau^2)$, где $\mu_\tau \in [0.25, 0.50]$ (тип-специфичные средние загрузки). Дополнительно каждый узел получает **постоянную личность (personality)** — смещение из $\mathcal{N}(0, 0.12^2)$, имитирующее «горячие» и «холодные» хосты.

2. **Пошаговое обновление**: на каждом шаге $t$:
$$x_t = x_{t-1} + \varepsilon_t + d_t, \quad \varepsilon_t \sim \mathcal{N}(0,\ \sigma_n^2),\quad d_t = A\,\sin\!\left(\frac{2\pi t}{T}\right)$$
где $\sigma_n = 0.01$ (Гауссов шум), $A = 0.015$ (амплитуда синусоидального дрейфа), $T = 30$ шагов (период). В датасете v4.9 использовалось $A = 0.03$; снижение до $0.015$ в v5a сузило здоровый фон (см. раздел 7).

3. **Зажим**: значения ограничиваются в $[0, 1]$.

4. **Healthy outliers**: наличие personality и синусоидального дрейфа гарантирует, что ≈1–2 % здоровых узлов в любой момент будут иметь заметно отклонившиеся значения. Это делает задачу реалистичной — нельзя объявлять любой аномальный узел RC.

**Зачем нужны шумные здоровые графы?** Если бы здоровые узлы имели идеально стабильные признаки, модель научилась бы использовать простой порог: «если `delta_long` > ε → RC». Такой ярлык потерял бы обобщающую способность на реальных данных. Шум и personality вынуждают модель использовать граф-контекст и временны́е паттерны.

### 4.2 Инъекция неисправности

Неисправность внедряется начиная с шага $t_0 = 50$ (константа `FAULT_INJECTION_STEP`). Для каждого выбранного канала $(v, f)$ с суммарной амплитудой $A_{\text{total}}$ и направлением $d \in \{+1, -1\}$:

$$\Delta_{t}(v,f) = d \cdot \frac{A_{\text{total}}}{\max(1,\, T - t_{\text{act}})}, \quad t \geq t_{\text{act}}$$

где $t_{\text{act}}$ — шаг активации аномалии (для RC = 50, для жертв — позже, с задержкой BFS-обхода топологии). Каждая аномалия распределяется равномерно по оставшимся 40 шагам, создавая плавный рамп. EMA частично адаптируется к нему, поэтому `delta_long` сохраняет умеренное постоянное значение, а не резкий пик — это соответствует поведению реальных метрик при нарастающей проблеме.

**Задержка жертв** вычисляется через BFS по физической топологии: каждый дополнительный hop добавляет случайную задержку $\delta \sim \text{TruncExp}(\lambda=0.15, \max=10)$ шагов, что воспроизводит реальное распространение аномалии через сеть.

### 4.3 Z-нормализация

После генерации выборки из здоровых графов вычисляется per-feature среднее $\mu_f$ и стандартное отклонение $\sigma_f$. Все признаки (здоровые и фолтед) затем нормируются:

$$x_{\text{norm}} = \frac{x - \mu_f}{\sigma_f + \varepsilon}, \quad \varepsilon = 10^{-6}$$

Нормализация вычисляется в пространстве четырёх каналов (value, delta\_short, delta\_long, rolling\_var) раздельно. После нормализации `delta_long` здорового узла имеет распределение $\approx \mathcal{N}(0, 1)$; аномальный RC-узел должен выделяться значимо выше нуля.

## 5. Типы неисправностей и паттерны инъекции

В датасете реализованы 9 типов неисправностей (константа `FAULT_TYPES` в `dataset_generator.py`). Тяжесть неисправности `severity` сэмплируется из $U(0.4, 1.0)$; базовая амплитуда $\text{amp} = \text{severity} \times k_\tau$, где $k_\tau$ — тип-специфичный коэффициент.

### 5.1 Описание каждого типа

---

**hdd\_degradation** (RC: `hdd`)

*Физика*: деградация магнитных пластин или головок — растут задержки, появляются перераспределённые секторы (SMART-атрибут).

| Канал | Направление | Роль |
|-------|------------|------|
| `disk_reallocated_sectors` | ↑ (3 рампы) | **Первичный** — уникален для деградации, disk\_full никогда не затрагивает |
| `disk_latency_ms` | ↑ (3 рампы) | **Первичный** — деградировавшие головки |
| `disk_temperature_celsius` | ↑ (2 рампы, мягко) | Вторичный |
| `disk_read_iops` | ↓ (1 рамп) | Вторичный — меньше операций при деградации |
| `cpu_iowait_percent` | ↑ (жертва, задержка 8–16 ш.) | Косвенный |

*Разделение с disk\_full*: disk\_full использует `disk_usage_percent` + `disk_write_iops` — ни одного общего первичного канала.

---

**network\_congestion** (RC: `switch`)

*Физика*: перегрузка коммутатора — потери пакетов, рост задержек, CRC-ошибки.

| Канал | Направление | Роль |
|-------|------------|------|
| `switch_packet_loss_percent` | ↑ (2 рампы) | **Первичный** — уникален для switch |
| `switch_latency_ms` | ↑ (2 рампы) | **Первичный** |
| `switch_bandwidth_usage_percent` | ↑ (1 рамп) | Первичный |
| `switch_crc_errors_count` | ↑ (1 рамп) | Вторичный — аппаратные ошибки |
| `cpu_iowait_percent` | ↑ (жертва, задержка 6–12 ш., амплитуда ≤0.15×amp) | Косвенный |

---

**ram\_leak** (RC: `ram`)

*Физика*: утечка памяти в процессе — монотонный рост потребления.

| Канал | Направление | Роль |
|-------|------------|------|
| `ram_used_percent` | ↑ (3 рампы медленно) | **Первичный** — монотонный рост |
| `ram_fragmentation_score` | ↑ (3 рампы) | **Первичный** — уникален для leak vs bw\_sat и swap |
| `ram_available_mb` | ↓ (2 рампы) | Вторичный |
| `ram_cached_mb` | ↓ (1 рамп) | Вторичный |
| `ram_page_faults_ps` | ↑ (1 рамп, поздно: +25–40 ш.) | Поздний вторичный |

*Разделение*: memory\_bw\_sat использует `ram_bandwidth_mb` + `ram_latency_ns`; swap\_thrashing — `ram_swap_used_percent` + `ram_page_faults_ps`.

---

**cpu\_frequency\_drop** (RC: `cpu`)

*Физика*: DVFS-регулятор снижает частоту P-состоянием (thermal/power cap).

| Канал | Направление | Роль |
|-------|------------|------|
| `cpu_frequency_mhz` | ↓ (4 ступени) | **Первичный** — ступенчатый паттерн P-state |
| `cpu_power_watts` | ↓ (3 ступени) | **Первичный** — $P \propto V^2 f$ |
| `cpu_temperature_celsius` | ↓ (2 ступени) | Вторичный — меньше мощности → меньше тепла |
| `cpu_user_percent` | ↑ (1 рамп, мягко) | Вторичный — нагрузка не упала, процессор работает медленнее |

*Разделение с cpu\_cache\_thrashing*: cache thrashing использует `cpu_context_switches_ps` + `cpu_usage_total_percent` как первичные; у cpu\_frequency\_drop нет context\_switches.

**cpu\_cache\_thrashing** (RC: `cpu`)

## 6. Проблема датасета v4.9: диагностика потолка Hit@1=63 %

### 6.1 Наблюдаемые симптомы

После 6 фаз оптимизации модели (унификация evaluator, диагностика ошибок, temperature scaling, hard negatives, обогащение данных, измерение type-gating) Hit@1 оставался на уровне 63–64 %. При этом наблюдалась характерная картина:

| Метрика | v4.9 full training |
|---------|-------------------|
| Hit@1 | 63.3 % |
| Hit@3 | 77.2 % |
| Hit@5 | 81.5 % |

Высокие Hit@3 и Hit@5 означали, что модель **часто включала RC в топ-3**, но не могла надёжно поставить его на первое место. Это указывало на проблему ранжирования, а не классификации.

### 6.2 Первоначальные гипотезы и их опровержение

| Гипотеза | Эксперимент | Результат |
|----------|------------|-----------|
| Cross-type calibration (разные шкалы скоров) | Per-type temperature scaling | +0.4pp → отклонена |
| Hard negative loss | Global hard-neg, α=0.1 | +1.3pp → слабо |
| Слабый сигнал у плохих типов | Увеличение числа рамп v4.9 | +2.4pp провизорно, целевые типы не улучшились |
| Type-gating (двухэтапная модель) | Stage-1 type accuracy | 45 % < 85 % → отклонена |

Все эти вмешательства лечили симптомы, а не причину.

### 6.3 Реальная причина: эффект порядковых статистик

Forensic-анализ сравнил `delta_long` RC-узла с максимальным `delta_long` среди здоровых узлов **того же типа в том же графе**:

| Тип неисправности | RC $\delta_{\text{long}}$, σ | Здоровый макс., σ | RC > фона | Hit@1 |
|---|---|---|---|---|
| disk\_full | 2.61 | 2.80 | **36 %** | 63 % |
| ram\_leak | 2.97 | 2.81 | **55 %** | 57 % |
| hdd\_degradation | 3.28 | 2.78 | **59 %** | 52 % |
| cpu\_frequency\_drop | 3.31 | 2.72 | 71 % | 53 % |
| gpu\_thermal\_throttle | 3.44 | 2.81 | 73 % | 73 % |

Для `disk_full` RC-узел был **слабее** случайных здоровых HDD-узлов в 64 % случаев! Модель физически не могла ранжировать его первым только по сигналу признаков.

**Объяснение через порядковые статистики**: при $N = 100$ узлов одного типа максимальное значение i.i.d. случайных величин $\mathcal{N}(0, 1)$ в среднем равно:

$$\mathbb{E}[\max_{i=1}^{N} Z_i] \approx \sqrt{2 \ln N} = \sqrt{2 \ln 100} \approx 3.03\,\sigma$$

Здоровые узлы всегда будут иметь хотя бы один с `delta_long` ≈ 3σ — просто в силу теории экстремальных значений. Чтобы RC надёжно оказывался выше этого порога, его сигнал должен быть $\geq 5$–$6\,\sigma$.

В v4.9 RC-сигналы находились на уровне 2.6–3.5σ — близко к здоровому максимуму, что и ограничивало потолок.

**Дополнительная проблема — жертвы-конкуренты**: в `disk_full` жертва `cpu_iowait` инжектировалась с амплитудой $0.75 \times \text{amp}$ — столь же сильной, как первичные RC-каналы. CPU-узел становился «ложным RC» и в 21 % промахов выигрывал ранжирование у HDD.

## 9. Архитектура модели

Реализована в `training_pipeline/train.py`, класс `GATv2Hetero`.

### 9.1 Схема сети

```
Входные признаки [N_τ × d_τ] → Linear(d_τ, H) → ELU  [N_τ × H]
                        ↓
              GATv2Conv (Layer 1, heads=4)
              + Residual + Dropout(0.1) + LayerNorm
                        ↓
              GATv2Conv (Layer 2, heads=4)
              + Residual + Dropout(0.1) + LayerNorm    [N_τ × H]
                        ↓
              SharedScorer                              [N_τ × 1]
```

Параметры модели: **316 882** (при `scorer_mode=shared`).

### 9.2 Слои внимания (GATv2Conv)

Используется GATv2 (Brody et al., 2022) в гетерогенном контексте через `HeteroConv`:

$$\alpha_{ij}^{(l)} = \text{softmax}_j\!\left(\mathbf{a}^\top \text{LeakyReLU}\!\left(\mathbf{W}_1 \mathbf{h}_i^{(l)} + \mathbf{W}_2 \mathbf{h}_j^{(l)}\right)\right)$$

Для каждого типа ребра $(s, r, t)$ обучается своя пара матриц $(\mathbf{W}_1, \mathbf{W}_2)$ (всего 16 × 2 = 32 матрицы). Агрегация — сумма по всем типам рёбер для целевого узла (`aggr="sum"` в `HeteroConv`).

**Гиперпараметры**: $H = 64$, heads = 4 (multi-head attention, скрытое пространство $H / \text{heads} = 16$ на голову), dropout = 0.1.

### 9.3 Residual + LayerNorm

После каждого GATv2-слоя:

$$\mathbf{h}_v^{(l+1)} = \text{LayerNorm}\!\left(\text{Dropout}\!\left(\mathbf{h}_v^{(l+1, \text{raw})}\right) + \mathbf{h}_v^{(l)}\right)$$

Residual connection обеспечивает устойчивость градиента при глубине 2 слоя; LayerNorm нормирует скрытые состояния per-узел, что важно при агрегации из разных типов рёбер с разными масштабами.

### 9.4 SharedScorer

Ключевое архитектурное решение. Вместо независимых линейных голов $\mathbf{w}_\tau^\top \mathbf{h}_v + b_\tau$ для каждого типа узла используется **единый MLP** с обучаемым эмбеддингом типа:

$$s_v = \text{MLP}\!\left([\mathbf{h}_v;\ \mathbf{e}_\tau]\right), \quad \mathbf{e}_\tau \in \mathbb{R}^{H/4}$$

Это создаёт **общее пространство ранжирования** для всех типов RC-кандидатов. При раздельных головах каждый тип оценивается независимо — модель не имела механизма сравнивать CPU vs HDD vs Switch, что приводило к систематической кросс-типовой ошибке. SharedScorer устраняет этот изъян.

### 9.5 Кандидаты на RC

К RC-кандидатам относятся: `cpu`, `gpu`, `ram`, `hdd`, `switch`. Узлы `job` и `rca_context` исключены из ранжирования — они являются жертвами или агрегаторами, но не источниками неисправностей.

## 10. Функция потерь

### 10.1 Ограничения BCE (старый подход)

Оригинальный вариант обучал **бинарную классификацию** независимо для каждого узла (BCEWithLogitsLoss). Это не соответствует реальной задаче: в каждом графе ровно один RC-узел, и задача — его идентифицировать **относительно** других кандидатов. Независимая BCE не создаёт конкуренцию между узлами разных типов.

### 10.2 Глобальная per-graph CrossEntropy

Реализована в `training_pipeline/train.py`, функция `compute_global_ce_loss`. Для каждого фолтед-графа $G$:

1. Собираются логиты всех RC-кандидатов в один вектор:
$$\mathbf{z} = [\underbrace{z_1^{(\text{cpu})}, \ldots, z_{N_{\text{cpu}}}^{(\text{cpu})}}_\text{100 cpu}, \underbrace{z_1^{(\text{gpu})}, \ldots}_\text{100 gpu}, \ldots, \underbrace{z_1^{(\text{switch})}, \ldots}_\text{6 switch}] \in \mathbb{R}^{406}$$

2. Потеря — кросс-энтропия с целевым индексом $k^* = \text{global index of RC node}$:
$$\mathcal{L} = -z_{k^*} + \log \sum_{k} \exp(z_k)$$

Это эквивалентно softmax-соревнованию: модель должна максимизировать скор **именно** RC-узла относительно всех остальных ~400 кандидатов. Gradient flow через всех конкурентов создаёт прямую конкуренцию между типами.

### 10.3 Проверенные расширения

**Hard negative loss** (Phase 4): добавлялся штраф за top-k конкурентов:
$$\mathcal{L}_{\text{hn}} = \frac{1}{k} \sum_{i \in \text{top-k}} \max(0,\ \text{margin} - z_{k^*} + z_i)$$
Результат: +1.3 пп Hit@1 при margin=0.5, k=5, α=0.1 — недостаточно.

**Temperature scaling** (Phase 3): per-type температуры $T_\tau$, скоры $z / T_\tau$. Обучались на половине val, оценивались на другой. Результат: +0.4 пп — ошибки кросс-типовые, а не глобально смещённые.

**Type-gating** (Phase 6): попытка двухэтапной модели (классификатор типа → ранжирование внутри типа). Измерена Stage-1 accuracy: 45 % (mean-pool head), implicit max-node: 68 %. Оба значительно ниже порога 85 %. Причина: `cpu`, `ram`, `hdd` неразличимы на уровне graph-pooling из-за общих victim-каналов (`cpu_iowait`, `job_runtime`). Метод отклонён.

## 11. Протокол обучения

Реализован в `training_pipeline/train.py`.

### 11.1 Разбиение данных

```python
# training_pipeline/eval_utils.py
def build_train_val_indices(n_total, train_ratio=0.80, seed=42):
    perm = torch.randperm(n_total, generator=torch.Generator().manual_seed(seed))
    split = int(n_total * train_ratio)
    return perm[:split].tolist(), perm[split:].tolist()
```

Используется исключительно `torch.randperm` с фиксированным seed=42. Принципиально важно: применение `numpy.random` вместо `torch` давало другую перестановку и завышало Hit@1 на 9 пп (ошибка была обнаружена и исправлена в Phase 1, `eval_utils.py` создан как единый источник истины).

| Параметр | Значение |
|---------|---------|
| Train/Val split | 80/20 |
| Seed | 42 (torch.randperm) |
| Batch size | 4 графа |
| Оптимизатор | AdamW |
| Learning rate | $10^{-3}$ |
| Weight decay | $10^{-4}$ |
| Screening (EPOCHS, PATIENCE) | 10, 3 |
| Full training (EPOCHS, PATIENCE) | 60, 8 |
| Checkpoint selection | по Hit@1 на val |

### 11.2 Screening vs Full training

**Screening** (EPOCHS≤10, PATIENCE≤3) — быстрая проверка, что новый датасет или гиперпараметр не деградирует. Занимает ~10–15 минут. Checkpoint сохраняется, результаты фиксируются в отчёт. К полному обучению переходят только при прохождении gate-критериев (Hit@1 ≥ 68 % или Hit@3 ≥ 75 %).

**Full training** (EPOCHS=60, PATIENCE=8) — финальное обучение; занимает ~2.5 часа. Ожидаемый прирост vs screening: +2–4 пп за счёт большего числа эпох и менее жёсткого ранней остановки.

### 11.3 Что исключается из RCA-метрик

Healthy-графы имеют `fault_type_idx = -1`. В `eval_utils.run_evaluation()` они **пропускаются** при расчёте Hit@k и MRR — модель их видит в обучении (различение healthy vs faulted является частью задачи), но не оценивается на них по RCA-задаче.

### 11.4 Зачем per-fault разбивка обязательна

Глобальное Hit@1 может скрывать катастрофические провалы на отдельных типах. Пример из v4.9: глобальное Hit@1=63 % маскировало 51 % на `hdd_degradation` и 53 % на `cpu_frequency_drop`. Полный per-fault breakdown в каждом отчёте — обязательное условие честной оценки.

## 12. Метрики оценки

Реализованы в `training_pipeline/eval_utils.py`, функция `compute_rca_report()`.

### 12.1 Hit@k

$$\text{Hit@}k = \frac{1}{|\mathcal{G}_{\text{faulted}}|} \sum_{G \in \mathcal{G}_{\text{faulted}}} \mathbf{1}[\text{rank}(v_{\text{RC}}^G) \leq k]$$

где $\text{rank}(v_{\text{RC}}^G)$ — позиция RC-узла в убывающем ранжировании скоров всех кандидатов.

### 12.2 MRR (Mean Reciprocal Rank)

$$\text{MRR} = \frac{1}{|\mathcal{G}_{\text{faulted}}|} \sum_{G \in \mathcal{G}_{\text{faulted}}} \frac{1}{\text{rank}(v_{\text{RC}}^G)}$$

MRR строже, чем Hit@1: даже если RC стоит на первом месте, MRR = 1.0 только для всех графов. Полезен для сравнения моделей с одинаковым Hit@1 но разным распределением ошибок.

### 12.3 Median rank

Медиана по $\text{rank}(v_{\text{RC}}^G)$ — устойчивая к выбросам характеристика. В обоих датасетах = 1 (RC стоит первым в большинстве графов), но хвост распределения различается.

### 12.4 Macro vs Micro

**Micro**: стандартное усреднение по всем графам (с учётом дисбаланса fault types).  
**Macro**: усреднение по типам неисправностей (каждый тип с весом 1/9), независимо от числа примеров.

$$\text{macro-Hit@1} = \frac{1}{9} \sum_{\tau} \text{Hit@1}_\tau$$

Macro-метрика важна для выявления «молчащих» типов: если `ram_leak` (42 графа) получает 0 %, а `network_congestion` (87 графов) — 100 %, micro-Hit@1 будет выглядеть прилично.

### 12.5 Почему Hit@3 важен для практики

В сценарии RCA-ассистента оператор получает топ-3 предположения о первопричине. Если RC находится в топ-3, инцидент скорее всего будет диагностирован — оператор проверит все три кандидата. Поэтому Hit@3 является операционно значимой метрикой наряду с Hit@1.

## 13. Эксперименты, не решившие проблему

| Эксперимент | Фаза | Реализация | Результат | Почему не сработало |
|-------------|------|------------|-----------|---------------------|
| Temperature scaling | Phase 3 | Per-type $T_\tau$, fitted на calib-half | +0.4 пп Hit@1 | Ошибки graph-specific, не глобально смещённые |

## 14. Финальный результат и интерпретация

### 14.1 Итоговое сравнение

| | v4.9 full training | v5a\_40 screening |
|---|---|---|
| **Hit@1** | **63.3 %** | **87.5 %** |
| Hit@3 | 77.2 % | 92.3 % |
| Hit@5 | 81.5 % | 93.8 % |
| MRR | 0.714 | 0.903 |
| Эпоха | 7 (из 60, patience=8) | 7 (из 10, patience=3) |
| $n_{\text{faulted}}^{\text{val}}$ | 534 | 534 |
| `healthy_ratio` | 0.40 | 0.40 |
| Unified evaluator | да | да |

+24.2 пп Hit@1 получены **без изменения архитектуры** и **без новых признаков** — только за счёт коррекции SNR датасета и ослабления контаминирующих жертв.

### 14.2 Почему результат честен

- Одинаковая доля фолтед-графов (0.60) и идентичный $n_{\text{faulted}}^{\text{val}} = 534$.
- Единый evaluator (`eval_utils.py`) с `torch.randperm(seed=42)` — bug RNG-разбиения исправлен в Phase 1.
- Никакого прямого доступа к меткам при построении признаков.
- Сравнение проводится на **val split**, не на train split.
- v5a\_70 (промежуточный, `healthy_ratio=0.70`) признан некорректным для сравнения и не используется как финальный результат.

### 14.3 Физическая интерпретация

Улучшение объясняется тем, что модель теперь получает **достаточный SNR**:

- RC-узлы в v5a\_40: $\delta_{\text{long}} \in [4, 6]\,\sigma$ vs здоровый max ≈ $2.8\,\sigma$ → зазор $\geq 1.5\,\sigma$.
- В v4.9: RC ≈ $3\,\sigma$ vs max ≈ $2.75\,\sigma$ → зазор ≈ $0.25\,\sigma$ (в пределах шума).

GATv2-архитектура и global CE loss были правильными изначально; узким местом был синтетический датасет с недостаточным контрастом между RC и здоровым фоном.

## 15. Ограничения

1. **Синтетические данные**: все результаты получены на симулированной телеметрии. Физические паттерны (ступенчатый DVFS, CRC-ошибки) приближены, но не тождественны реальным метрикам. Validirование на реальных трейсах суперкомпьютера (JINR, Lomonosov, Polus) является необходимым следующим шагом.

2. **Прокси-признаки**: `ram_fragmentation_score`, `disk_reallocated_sectors`, `gpu_ecc_errors_count` симулируются как нормированные числа в [0, 1]. Реальные значения (например, SMART-атрибут 197 в секторах) имеют другое распределение и пороговые значения.

3. **Регрессия `memory_bandwidth_saturation`**: −2.2 пп Hit@1 в v5a\_40 vs v4.9 (63.8 % vs 66.0 %). Причина — возможное изменение нормализации при снижении `_DRIFT_AMP`. Требует мониторинга при полном обучении.

4. **Screening vs full training**: результат 87.5 % Hit@1 — скрининг (10 эпох), а не финальное обучение (60 эпох). Ожидается дополнительный прирост +2–4 пп.

5. **Нет данных о частоте ошибок типа I**: healthy-графы показаны модели в обучении, но RCA-метрики healthy-графов не измеряются. Процент ложных тревог (false alarms) на реальных данных неизвестен.

## 16. Направления дальнейших исследований

### 16.1 Ближайшие шаги (в рамках текущего пайплайна)

- **Полное обучение на v5a\_40** (EPOCHS=60, PATIENCE=8): ожидаемый финальный Hit@1 = 89–92 %.
- **Мониторинг `memory_bandwidth_saturation`**: при Hit@1 < 60 % — целевое усиление RC-каналов (`ram_bandwidth_mb`, `ram_latency_ns`).
- **Связка GNN → RAG/LLM**: после инференса GNN передаёт топ-3 RC-кандидатов в LLM-пайплайн с SOP-документами (Mistral-интеграция, реализована в `d:/Vlad/JINR-rag`).

### 16.2 Расширение признаков (схема v5b)

Новые признаки потребуют изменения `FEATURE_SCHEMA` в `config.py` и переобучения с нуля:

| Признак | Тип узла | Помогает | Реалистичность |
|---------|---------|---------|----------------|
| `cpu_run_queue_length` | cpu | cpu\_cache\_thrashing vs cpu\_freq\_drop | Да (Linux: `/proc/loadavg`) |
| `ram_numa_remote_access_percent` | ram | memory\_bw\_sat | Да (perf counters) |
| `disk_pending_sectors` | hdd | hdd\_degradation (SMART attr. 197) | Да |
| `disk_read_errors_count` | hdd | hdd\_degradation | Да |
| `gpu_throttle_reason_encoded` | gpu | gpu\_thermal\_throttle | Да (NVML) |
| `job_slowdown_ratio` | job | все типы | Да (SLURM: estimated vs actual runtime) |

### 16.3 Валидация на реальных данных

Предлагаемый план:
1. Собрать телеметрию кластера (Prometheus/Grafana) за период известных инцидентов.
2. Согласовать метрики с синтетической схемой признаков.
3. Дообучить модель на реальных трейсах (если разметка доступна) или применить zero-shot.
4. Измерить Hit@k на реальных инцидентах.
